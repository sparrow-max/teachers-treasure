## 1. 职责与边界

后端是**唯一业务规则实现方**，职责包括：

1. 接收并校验前端请求（Pydantic）。
2. 实现点名场次状态流转、签到幂等、缺勤生成。
3. 通过 Repository 与数据库交互，管理事务。
4. 统一响应封装、错误码、日志。
5. 自动生成 OpenAPI，供前端生成类型与联调。

**不负责**：页面渲染、前端状态、权限登录（MVP 无鉴权）。

## 4. 接口详细设计

### 4.0 统一响应与异常

所有接口返回：

```json
{ "code": 0, "message": "success", "data": {} }
```

失败：

```json
{ "code": 40901, "message": "该学号已存在", "data": null }
```

- 业务异常统一抛 `ApiError(code, message, http_status)`，由全局异常处理器转换为上述结构。
- Pydantic 校验失败映射为 `40001`，`message` 取第一条可读错误，`data` 中可附带 `fields`（可选，前端不强制使用）。
- 未捕获异常：记录 `request_id` 与堆栈，返回 `50000`，不暴露内部细节。

**中间件**：为每个请求生成 `request_id`（UUID），写入响应头 `X-Request-ID` 与日志。

### 4.1 GET `/api/v1/health`

- 用途：存活检查。
- 请求：无。
- 成功 200：

```json
{ "code": 0, "message": "success", "data": { "status": "ok", "version": "1.0.0" } }
```

- 失败：无（数据库不可用时也返回 200，`status` 可为 `degraded`，避免探针误杀；可选）。

---

### 4.2 GET `/api/v1/students`

- 用途：获取学生名单。
- Query：

| 参数 | 类型 | 必填 | 默认 | 校验 |
| --- | --- | --- | --- | --- |
| `keyword` | string | 否 | — | 长度 ≤ 32，匹配姓名或学号模糊查询 |
| `active` | boolean | 否 | `true` | 是否只返回在册学生 |

- 成功 200：

```json
{
  "code": 0,
  "message": "success",
  "data": [
    {
      "id": 1,
      "student_no": "20230001",
      "name": "张三",
      "role": "学生",
      "active": true,
      "created_at": "2026-11-05T10:00:00+08:00"
    }
  ]
}
```

- 排序：`student_no ASC, id ASC`。
- 错误：`40001`（keyword 超长）。

**说明**：名单接口不分页，MVP 单课堂人数 ≤ 200，直接返回全量；若后续超过 500 人再增加分页（需走契约变更）。

---

### 4.3 POST `/api/v1/students`

- 用途：添加学生。
- 请求体：

```json
{ "student_no": "20230001", "name": "张三", "role": "学生" }
```

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `student_no` | string | 是 | 1–32 字符，正则 `^[A-Za-z0-9_-]+$`，去除首尾空格 |
| `name` | string | 是 | 1–32 字符，去除首尾空格，不允许纯空白 |
| `role` | string | 否 | 枚举 `学生`/`班长`/`教师`，默认 `学生` |

- 成功 201：返回 `Student` 完整对象。
- 错误：
  - `40001`：字段缺失、超长、学号格式非法。
  - `40901`：`student_no` 已存在（包含已软删除学生，学号全局唯一不可复用）。

**实现要点**

1. 先 `strip()`，再校验。
2. 依赖数据库唯一约束兜底，捕获 `IntegrityError` 并转为 `40901`，避免并发重复。
3. 不信任前端传入的 `id`、`active`、`created_at`。

---

### 4.4 DELETE `/api/v1/students/{student_id}`

- 用途：从名单移除学生（软删除，保留历史记录）。
- 路径参数：`student_id` 正整数。
- 成功 200：

```json
{ "code": 0, "message": "success", "data": { "id": 1, "deleted": true } }
```

- 错误：
  - `40401`：学生不存在或已删除。
- 实现：`UPDATE students SET active = false WHERE id = :id AND active = true`；`rowcount=0` 返回 `40401`。
- 不影响已创建场次的 `attendance_records`（记录存快照）。

> 不提供修改学生接口（MVP）。若后续新增，必须更新契约与前端类型。

---

### 4.5 POST `/api/v1/rollcalls`

- 用途：开始点名，创建场次并为当前在册学生生成 `pending` 记录。
- 请求体：

```json
{ "title": "2026-11-05 课堂点名", "order_by": "student_no" }
```

| 字段 | 类型 | 必填 | 默认 | 校验 |
| --- | --- | --- | --- | --- |
| `title` | string | 否 | 服务端生成 `YYYY-MM-DD 课堂点名` | 1–64 字符 |
| `order_by` | string | 否 | `student_no` | 枚举 `student_no` / `name` / `id` |

- 成功 201：返回 `SessionDetail`。
- 错误：
  - `40001`：`order_by` 非法、title 超长。
  - `40905`：当前 `active = true` 的学生数为 0。

**事务步骤（必须在同一事务）**

1. 查询 `students WHERE active = true`，按 `order_by` 排序；为 0 则抛 `40905`。
2. 插入 `rollcall_sessions`：`status='calling'`、`started_at=now()`、`order_by`、`title`。
3. 按排序结果批量插入 `attendance_records`：`order_no` 从 1 递增，`status='pending'`，写入 `student_no/student_name/role` 快照，`checked_at=NULL`。
4. 提交后重新查询场次与记录，聚合统计后返回。

**排序实现**

| order_by | SQL 排序 |
| --- | --- |
| `student_no` | `student_no ASC, id ASC` |
| `name` | `name ASC, id ASC`（中文按数据库排序规则；SQLite 为二进制序，可接受） |
| `id` | `id ASC` |

- 成功响应示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "session": {
      "id": 10,
      "title": "2026-11-05 课堂点名",
      "status": "calling",
      "order_by": "student_no",
      "started_at": "2026-11-05T10:00:00+08:00",
      "ended_at": null,
      "total_count": 3,
      "present_count": 0,
      "absent_count": 0,
      "pending_count": 3
    },
    "records": [
      {
        "id": 100,
        "session_id": 10,
        "student_id": 1,
        "student_no": "20230001",
        "student_name": "张三",
        "role": "学生",
        "order_no": 1,
        "status": "pending",
        "checked_at": null
      }
    ]
  }
}
```

### 4.7 GET `/api/v1/rollcalls/{session_id}`

- 用途：场次详情，供页面刷新恢复、轮询、历史明细。
- 成功 200：`SessionDetail`，`records` 按 `order_no ASC` 排序。
- 错误：`40402` 场次不存在。
- 性能：单场次 ≤ 200 条记录，一次查询 + 内存聚合即可；不使用 N+1。

### 4.8 POST `/api/v1/rollcalls/{session_id}/checkin`

- 用途：学生签到。
- 请求体：

```json
{ "student_id": 1 }
```

- 成功 200：返回更新后的 `Record`：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 100,
    "session_id": 10,
    "student_id": 1,
    "student_no": "20230001",
    "student_name": "张三",
    "role": "学生",
    "order_no": 1,
    "status": "present",
    "checked_at": "2026-11-05T10:01:20+08:00"
  }
}
```

- 错误：

| 场景 | code | HTTP |
| --- | --- | --- |
| 场次不存在 | 40402 | 404 |
| 场次已结束 | 40903 | 409 |
| 学生不在该场次 | 40904 | 409 |
| 已签到 | 40902 | 409 |

**并发安全实现（推荐原子更新）**

```sql
UPDATE attendance_records
SET status = 'present', checked_at = :now
WHERE session_id = :session_id
  AND student_id = :student_id
  AND status = 'pending';
```

- `rowcount = 1`：成功，查询并返回记录。
- `rowcount = 0`：按顺序诊断——场次不存在 → 40402；场次 `ended` → 40903；记录不存在 → 40904；记录已 `present` → 40902。
- 时间由服务端生成（UTC），不得使用前端时间。

---

### 4.9 POST `/api/v1/rollcalls/{session_id}/end`

- 用途：结束点名，未签到学生转缺勤。
- 请求体：无（如需备注可后续扩展，禁止现在加字段）。
- 成功 200：返回结束后的 `SessionDetail`（含签到与缺勤记录）。
- 错误：
  - `40402` 场次不存在。
  - `40903` 场次已结束（不可重复结束）。

**事务步骤（必须同一事务）**

```text
BEGIN
1. SELECT ... FROM rollcall_sessions WHERE id = :id FOR UPDATE   -- 不存在 → 40402
2. 若 status = 'ended' → 40903
3. UPDATE attendance_records
   SET status = 'absent', checked_at = :ended_at
   WHERE session_id = :id AND status = 'pending'
4. UPDATE rollcall_sessions
   SET status = 'ended', ended_at = :ended_at
   WHERE id = :id AND status = 'calling'
5. 重新聚合统计并读取 records
COMMIT
```

- `ended_at` 由服务端生成一次，签到与缺勤时间口径一致。
- SQLite 不支持 `FOR UPDATE`，由 SQLAlchemy 方言自动忽略；生产 PostgreSQL 生效。也可用条件更新 `WHERE status='calling'` 的 `rowcount` 防并发重复结束。

| 40401 | 404 | 删除学生时不存在 |

### 5.3 统计聚合

```sql
SELECT status, COUNT(*) AS cnt
FROM attendance_records
WHERE session_id = :session_id
GROUP BY status;
```

- `total_count = pending + present + absent`
- 场次列表使用窗口/子查询一次性聚合，避免每条场次单独查询（N+1）。

## 6. 数据校验规则

| 字段 | 规则 | 失败 code |
| --- | --- | --- |
| `name` | `strip` 后 1–32 字符，非纯空白 | 40001 |
| `student_no` | `strip` 后 1–32，`^[A-Za-z0-9_-]+$` | 40001 |
| `role` | 枚举：`学生`、`班长`、`教师` | 40001 |
| `title` | `strip` 后 1–64 字符 | 40001 |
| `order_by` | 枚举：`student_no`、`name`、`id` | 40001 |
| `page` | ≥ 1 | 40001 |
| `page_size` | 1–100 | 40001 |
| `status`（查询） | `calling`、`ended` | 40001 |
| `student_id` / `session_id` | 正整数 | 40001 |

- 所有字符串输出前不做 HTML 转义（JSON），由前端渲染时转义；后端不返回富文本。
- 日志中姓名与学号可记录，但不记录请求体全文（避免批量个人信息泄露）。

## 7. 事务与并发

| 场景 | 隔离要求 | 措施 |
| --- | --- | --- |
| 添加学生 | 唯一约束 | 捕获 `IntegrityError` → 40901 |
| 开始点名 | 一致性 | 单事务插入场次 + 记录；失败整体回滚 |
| 签到 | 防重复 | 条件更新 `WHERE status='pending'`，依据 `rowcount` |
| 结束点名 | 防重复结束 | 条件更新 `WHERE status='calling'` + 事务 |
| 并发签到与结束 | 不丢数据 | 结束只更新 `pending`；签到只更新 `pending`；二者必有一方生效 |

- 默认隔离级别：PostgreSQL `READ COMMITTED`；SQLite 使用默认串行写。
- 不在应用层做"先查后改"的唯一性判断作为最终依据，数据库约束与条件更新才是权威。

## 10. 测试计划

### 10.1 测试环境

- 内存 SQLite（`sqlite:///:memory:`），每个测试用例独立建表。
- FastAPI `TestClient`，覆盖统一响应结构。

### 10.2 必测用例

**学生**

1. 添加学生成功 → 201，字段完整，`role` 默认"学生"。
2. 重复学号 → 409 / 40901。
3. 空姓名、超长姓名、非法学号 → 400 / 40001。
4. 列表按学号升序；`keyword` 模糊匹配；`active=false` 过滤正确。
5. 删除学生 → `active=false`；再次删除 → 40401；已删除学生不出现在默认列表。

**点名**

6. 空名单开始点名 → 409 / 40905，且不创建场次。
7. 开始点名 → 201；`total_count = pending_count = 在册人数`；`order_no` 连续从 1 开始。
8. 签到成功 → `present`，`checked_at` 非空；统计 `present_count +1`、`pending_count -1`。
9. 重复签到 → 409 / 40902，记录仍只有一条。
10. 非本场学生签到 → 409 / 40904。
11. 结束点名 → 所有 `pending` 变 `absent`；`present + absent = total`；`ended_at` 非空。
12. 结束后签到 → 409 / 40903。
13. 重复结束 → 409 / 40903。
14. 场次不存在 → 404 / 40402。
15. 历史分页：`total/page/page_size` 正确，按开始时间倒序。

**并发**

16. 同一学生并发签到两次，仅一次成功，记录唯一。
17. 并发签到与结束，最终状态一致，无 `pending` 残留。

### 10.3 契约测试

- CI 导出 `openapi.json`，与《总体架构.md》第 7 章字段表人工/脚本比对。
- 响应字段禁止多出未登记字段（可增加 CI 脚本校验关键路径字段集合）。
